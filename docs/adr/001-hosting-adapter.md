# ADR ০০১ — হোস্টিং অ্যাডাপ্টার: @cloudflare/next-on-pages থেকে কোথায় যাবে?

- **স্টেটাস:** খসড়া (Draft)
- **তারিখ:** ২০২৬-১০-০৩
- **সিদ্ধান্ত নেবে:** প্রজেক্ট মালিক
- **সম্পর্কিত ডক:** `docs/audits/p3-secrets-deploy-findings.md` (সিক্রেট-ফ্লো অডিট — এই ADR-এর env-কৌশল আলোচনার পূর্বশর্ত)

## ১. প্রসঙ্গ (Context)

JxShoes বর্তমানে এভাবে ডেপ্লয় হয়:

- Next.js **14.2** (App Router), প্রায় সব API রাউটে `export const runtime = 'edge'` (যেমন `src/app/api/ai/route.ts`, `src/app/api/upload/route.ts`, `src/app/api/media/[file]/route.ts`, `src/app/api/cron/*/route.ts`)।
- বিল্ড অ্যাডাপ্টার: **`@cloudflare/next-on-pages@1.13.16`** (devDependency, `package.json`) — GitHub Actions (`.github/workflows/deploy.yml:53`) এ `npx @cloudflare/next-on-pages` চালিয়ে `.vercel/output/static` আউটপুট **Cloudflare Pages**-এ (প্রজেক্ট `shopkeeperbd`) ডেপ্লয় করে (deploy.yml:60)।
- Cloudflare-নির্ভর সব কাজ (KV, R2, Workers AI, Email) **REST API টোকেন দিয়ে** হয় — বাইন্ডিং নয়। এর কারণ হিসেবে `docs/AI_SYSTEM.md`-এ লেখা আছে: next-on-pages বিল্ডে অতিরিক্ত wrangler কনফিগ লাগে না।
- সিক্রেট ইনজেকশন: deploy.yml বিল্ডের সময় `src/lib/generatedEnv.ts` জেনারেট করে সিক্রেটগুলো **কম্পাইল-টাইম কনস্ট্যান্ট** হিসেবে এজ বান্ডেলে বেক করে (বিস্তারিত অডিট ডকে)।

**ট্রিগারিং ঘটনা:** `@cloudflare/next-on-pages`-এর অফিসিয়াল GitHub রিপো এখন ডেপ্রিকেটেড ঘোষণা করা হয়েছে এবং **২ অক্টোবর ২০২৬-এ আর্কাইভ করা হয়েছে** (read-only)। README-তে সরাসরি লেখা: *"The @cloudflare/next-on-pages package is deprecated and this repository is archived."* অর্থাৎ বর্তমান ডেপ্লয় পথ আর maintain হচ্ছে না — কোনো নিরাপত্তা-প্যাচ, Next.js নতুন ভার্সন সাপোর্ট বা বাগফিক্স আর আসবে না। সিদ্ধান্ত না নিলে প্রজেক্ট একটা মৃত অ্যাডাপ্টারে আটকে থাকবে (কাজ করবে, কিন্তু হিমায়িত)।

## ২. বিকল্পসমূহ

### বিকল্প (ক) — বর্তমান অবস্থায় থাকা: next-on-pages + Pages

**প্রো:**
- মাইগ্রেশন খরচ শূন্য; প্রোডাকশন আজ স্থিতিশীল (ROADMAP অনুযায়ী KV/AI/cron সব লাইভ ভেরিফায়েড)।
- পুরো অ্যাপ edge-runtime মডেলে লেখা — next-on-pages-এর সাথে পুরোপুরি সামঞ্জস্যপূর্ণ।
- REST-টোকেন ডিজাইন অ্যাডাপ্টার-অজ্ঞেয়বাদী (adapter-agnostic): KV/R2/AI কলগুলো সাধারণ `fetch` — অ্যাডাপ্টার বদলালেও লজিক অপরিবর্তিত থাকে।
- Pages-এর ফ্রি টিয়ার বিলিং অপরিবর্তিত থাকে।

**কন:**
- অ্যাডাপ্টার **আর্কাইভড/ডেপ্রিকেটেড** — নতুন Next.js ভার্সন (১৫/১৬) সাপোর্ট কখনোই আসবে না; Next 14 নিজেই আপস্ট্রিমে EOL-পথে, আর ROADMAP-এ চিহ্নিত Next.js সিকিউরিটি আপগ্রেড (ROADMAP.md:112–114) এই পথে সম্ভব নয়।
- Cloudflare-এর নতুন সব বিনিয়োগ Workers-এ; Pages শুধু রক্ষণাবেক্ষণ মোড।
- edge-runtime-এর সীমাবদ্ধতা স্থায়ী: Node.js API, `use cache`, ISR-ক্যাশিং ইত্যাদি নেই।
- দীর্ঘমেয়াদে নিরাপত্তা-ঝুঁকি: অ্যাডাপ্টারে ভবিষ্যতে CVE বের হলে প্যাচ পাওয়া যাবে না।

### বিকল্প (খ) — মাইগ্রেশন: `@opennextjs/cloudflare` (Workers)

OpenNext Cloudflare Adapters হলো কমিউনিটি-নির্দেশিত Workers-ভিত্তিক অ্যাডাপ্টার (cloudflare + Vercel-অনুমোদিত OpenNext প্রজেক্টের অংশ)। ডক অনুযায়ী এটি next-on-pages-এর বিপরীতে **পুরো Next.js ফিচার-সেট** সাপোর্ট করে এবং Node.js রানটাইম ব্যবহার করে।

**প্রো:**
- সক্রিয়ভাবে maintain হয়; App Router, Route Handlers, SSR/SSG, ISR, Middleware, Image Optimization (Cloudflare Images), PPR, `use cache`, `after` — সব সাপোর্টেড।
- Workers-এ **বাইন্ডিং** (KV/R2/AI/Secrets) সরাসরি পাওয়া যায় → P3 অডিটের "বান্ডেলে বেক করা ফুল-পারমিশন টোকেন" সমস্যার কাঠামোগত সমাধান সহজ হয় (REST থেকে বাইন্ডিং-এ যাওয়ার ক্যান্ডিডেটগুলো দেখুন অডিট ডকে)।
- Node.js রানটাইম → edge-runtime সীমাবদ্ধতা (যেমন `Buffer` ব্যবহার, `src/app/api/upload/route.ts:44`) আর সমস্যা নয়; ভবিষ্যতে Next 15/16 আপগ্রেডের পথ খোলা।
- cron Worker (`workers/report-cron`) মূল Worker-এর `crons` কনফিগে মার্জ করা যায় — এক ডেপ্লয় ইউনিট।

**কন / ঝুঁকি:**
- **Next.js 14 সাপোর্ট সংকুচিত হচ্ছে:** OpenNext ডক বলছে Next.js 16 ও Next 14/15-এর লেটেস্ট মাইনর সাপোর্টেড, তবে *"Next.js 14 support will be dropped Q1 2026"* — অর্থাৎ মাইগ্রেশনের সময় Next 15/16-এ ওঠাও একসাথে ভাবতে হবে (বা অন্তত 15-এর প্যাচড লেটেস্ট মাইনরে)। এটা breaking-change ঝুঁকি বাড়ায় (ROADMAP-এর Next আপগ্রেড আইটেমের সাথে জোড়া দিতে হবে)।
- edge-runtime রাউটগুলোর `runtime = 'edge'` ডিরেক্টিভ OpenNext-এ অপ্রয়োজনীয়/অনাকাঙ্ক্ষিত — OpenNext ডক পরামর্শ দেয় Node.js রানটাইম ব্যবহার করতে; সব রাউট থেকে ডিরেক্টিভ সরাতে হবে এবং আচরণ পরীক্ষা করতে হবে।
- `process.env`/`GENERATED_ENV` কৌশল বদলাতে হবে → `env` বাইন্ডিং-ভিত্তিক অ্যাক্সেস; `src/lib/cfEnv.ts`-এর একক-প্রবেশদ্বার ডিজাইন এখানে সাহায্য করবে (এক ফাইল বদলালেই হবে)।
- Node.js `Buffer`/crypto আচরণ, streaming SSE (`/api/ai` চ্যাট), `middleware.ts`-এর কুকি-চেক — প্রতিটা রিগ্রেশন-টেস্ট দরকার।
- CI রিরাইট: `deploy.yml`-এ next-on-pages স্টেপ বাদ দিয়ে `opennextjs-cloudflare build` + `wrangler deploy`; Pages প্রজেক্ট থেকে Workers-এ ডোমেইন/কাস্টম-ডোমেইন স্থানান্তর।

### বিকল্প (গ) — `vinext` (Cloudflare-এর বর্তমান ডিফল্ট সুপারিশ)

Cloudflare-এর Workers ডক (framework-guides → Next.js) এখন লেখা: *"Cloudflare recommends vinext as the default way to run Next.js applications on Cloudflare Workers"* — Vite-ভিত্তিক Next.js API রিইমপ্লিমেন্টেশন। তবে এটি এখনো **বেটা**; ডক নিজেই প্রোডাকশনে নেওয়ার আগে `npx vinext check` কম্প্যাটিবিলিটি-চেক চালাতে বলে।

- **প্রো:** Cloudflare-এর সাম্প্রতিকতম দিকনির্দেশ; next-on-pages থেকে মাইগ্রেশন গাইড দেওয়া আছে।
- **কন:** বেটা — একটা লাইভ বাণিজ্যিক দোকান + অ্যাডমিন প্যানেলের জন্য আজই ঝুঁকিপূর্ণ; ইকোসিস্টেম এখনো কাঁচা।

## ৪. সুপারিশ (Recommendation)

**দুই-ধাপে যাওয়া:**

1. **এখনই (সপ্তাহ ০–২):** অ্যাডাপ্টার বদলানোর আগেই P3 অডিটের সুপারিশ বাস্তবায়ন করো — next-on-pages-এর `getCloudflareContext()` দিয়ে **বাইন্ডিং** (KV/R2/AI) চালু করা, ফুল-পারমিশন টোকেন বান্ডেল থেকে বাদ দিয়ে টোকেন রোটেশন। এই কাজ দুই অ্যাডাপ্টারেই ট্রান্সফারযোগ্য দক্ষতা/কাঠামো তৈরি করে — ঝুঁকিহ্রাস হয়, অপচয় হয় না। next-on-pages আর্কাইভড হলেও Pages প্ল্যাটফর্ম ও রানটাইম আপাতত চলছে, তাই এই ধাপ নিরাপদ।
2. **পরের নিয়মিত উইন্ডোতে (সপ্তাহ ৩–৬):** Next.js 15/16 আপগ্রেড + **`@opennextjs/cloudflare`-এ মাইগ্রেশন** একসাথে করো (ROADMAP-এর Next-আপগ্রেড আইটেমের সাথে মিলিয়ে)। `vinext` এখনো বেটা — সেটা মেয়োর হলে পরে আরেকবার মূল্যায়ন করা যাবে; OpenNext-এ গেলে Workers-এ থাকায় ভবিষ্যতে vinext-এ যাওয়ার পথও সংক্ষিপ্ত থাকে।

**সংক্ষেপে:** বর্তমান পথে থেকে যাওয়া কোনোভাবেই দীর্ঘমেয়াদি বিকল্প নয় (অ্যাডাপ্টার আর্কাইভড); লক্ষ্য হওয়া উচিত Workers + বাইন্ডিং; প্রশ্ন শুধু কখন ও কোন মধ্যবর্তী ধাপে।

## ৫. ওপেন ডিসিশন পয়েন্ট (মালিকের সিদ্ধান্ত লাগবে)

1. **টাইমলাইন:** কখন মাইগ্রেট করা হবে — ইমেইল ফিচার শেষ হওয়ার আগে না পরে?
2. **Next.js টার্গেট:** 15-এর প্যাচড লেটেস্ট, নাকি সরাসরি 16? (OpenNext 16-এ সবচেয়ে ভালো সাপোর্টেড।)
3. **vinext নাকি OpenNext:** মাইগ্রেশনের মুহূর্তে vinext-এর স্থিতিশীলতা পুনর্মূল্যায়ন করতে হবে — বেটা থেকে উঠে এলে Cloudflare-এর ডিফল্ট পথেই যাওয়া যুক্তিযুক্ত।
4. **ISR/ক্যাশিং দরকার কি?** Durable Object-ভিত্তিক incremental cache লাগবে কি না (ফ্রি টিয়ারে DO সীমিত) — স্টোরফ্রন্ট বেশিরভাগ ডাইনামিক KV-নির্ভর, সম্ভবত লাগবে না; সিদ্ধান্ত মাইগ্রেশনের সময়।
5. **বাইন্ডিং-প্রথম নাকি মাইগ্রেশন-প্রথম:** ধাপ ১ (বাইন্ডিং) কি Pages-এই করা হবে, নাকি সরাসরি Workers-এ গিয়ে একসাথে? (এই ADR ধাপ ১-কে Pages-এ করার পক্ষে — ছোট ঝুঁকি, তাড়াতাড়ি সিক্রেট-ঝুঁকি হ্রাস।)
